# Полное описание проекта Brewery

## 1. Назначение и контекст проекта

Проект **Brewery** разработан в рамках дисциплины «Методы и средства проектирования информационных систем» (кафедра ИС, СПбГЭТУ «ЛЭТИ»). 

Это модульный масштабируемый REST API сервис для управления пивоваренным производством, сочетающий в себе функции:
- **PLM/PDM (Product Lifecycle / Data Management)**: ведение классификатора изделий, управление составом изделий (BOM — Bill of Materials), наследование атрибутов и версионирование/модификации изделий.
- **MES/CAPP (Computer-Aided Process Planning)**: маршрутная технология, технологические операции, привязка оборудования и рабочих центров, параметры технологических режимов.
- **Калькуляция себестоимости**: расчет полной производственной себестоимости партии продукции (сырьевая себестоимость по нормам расхода + трудозатраты с учетом квалификационных ставок рабочих).

## 2. Архитектура и стек технологий

Проект спроектирован по принципам **Clean Architecture** (чистая слоистая архитектура) с разделением ответственности и инверсией зависимостей через интерфейсы.

### 2.1 Стек технологий
- **Язык**: Go (1.24+)
- **HTTP фреймворк**: Gin с поддержкой graceful shutdown
- **База данных**: PostgreSQL 16
- **Слой доступа к данным**:
  - `pgx/v5` — высокопроизводительный драйвер PostgreSQL и пул соединений (`pgxpool`).
  - `sqlc` — кодогенерация типобезопасного Go-кода на основе статических SQL-запросов.
  - `squirrel` — построитель динамических SQL-запросов (сложная фильтрация, частичные обновления).
- **Миграции**: `goose` (встроенные в бинарник SQL-скрипты миграций с триггерами и тестовыми данными).
- **Документация API**: OpenAPI 3.0 / Swagger UI (`api/services.openapi.json`).
- **Инфраструктура и мониторинг**: Docker Compose, Nginx (reverse proxy), Prometheus (сбор метрик), Grafana (дашборды).
- **Тестирование**: `testing`, `testify`, `minimock` (генерация моков интерфейсов).

## 3. Модель предметной области и данных (ERD)

Система базируется на концепции единого классификатора, динамических атрибутов (паттерн EAV с типизацией), иерархических спецификаций и технологических маршрутов.

```
       +------------------+
       |     classes      |<------------------+
       +------------------+                   |
          |            |                      |
          |            |                      |
          v            v                      |
  +-------------+   +-------------------+     |
  |  products   |   | range_parameters  |     |
  +-------------+   |  enum_parameters  |     |
     |        |     +-------------------+     |
     |        |        |                      |
     v        v        v                      |
  +-------------+   +--------------------+    |
  |  materials  |   |products_parameters |    |
  +-------------+   +--------------------+    |
     |                                        |
     v                                        |
  +-------------+       +--------------+      |
  | operations  |------>| work_centers |      |
  +-------------+       +--------------+      |
     |       |                                |
     |       +--------------------------------+
     v
  +-----------------------+
  | operations_parameters |
  +-----------------------+
```

### 3.1 Ключевые сущности:

1. **Классификатор (`classes`)**:
   - Единое иерархическое дерево категорий (`id`, `name`, `parent_id`, `numeric_parameter_ids`, `enum_parameter_ids`).
   - Ограничение: единственный корень дерева.
   - Три основные ветви:
     - `products` (сырье, полуфабрикаты, готовое пиво);
     - `operation` (виды технологических операций: затирание, варка, фильтрация, розлив);
     - `profession` (профессии исполнителей: пивовар, технолог, оператор линии).
2. **Параметры и EAV-модель**:
   - **`range_parameters`**: диапазонные числовые параметры (`min_val`, `max_val`, `unit`, `field_name`, `inheritable`).
   - **`enum_parameters`** и **`parameter_values`**: списочные параметры с позиционированием значений (`enum_type`, `field_name`, `inheritable`, `value_raw`, `position`).
   - Наследование параметров: если флаг `inheritable = true`, параметры родительского класса автоматически наследуются дочерними классами (поддерживается триггерами БД).
   - **`products_parameters`** и **`operations_parameters`**: конкретные значения параметров, привязанные соответственно к изделиям или к технологическим операциям. Проверяются ограничениями CHECK (заполнено строго числовое значение или значение из справочника enum).
3. **Изделия (`products`)**:
   - `name`, `amount`, `units`, `class_id`, `base_id` (ссылка на базовое изделие для модификаций), `price` (закупочная цена для сырья/тары), `is_purchased` (признак покупного сырья), `is_final_product` (признак готовой продукции).
4. **Спецификация состава / BOM (`materials`)**:
   - Таблица связей `(material_id, product_id, material_amount, base)`.
   - Позволяет строить многоуровневое дерево входимости (например: *Хмель + Вода + Солод $\to$ Охмеленное сусло $\to$ Нефильтрованное пиво $\to$ Бутылка 0.5л*).
   - Поле `base = true` отмечает базовую норму, унаследованную от базового изделия при создании модификации.
5. **Оборудование (`work_centers`)**:
   - Сущность производственного оборудования с составным первичным ключом: `(equipment_name, work_center_name)` (например, *«Котел ВК-501», «Варочный цех»*).
6. **Маршрутная технология (`operations`)**:
   - Шаг технологического маршрута изготовления полуфабриката или готового изделия:
     - `output_product_id` — выпускаемое изделие;
     - `input_product_id` — потребляемый на данном шаге компонент; пара `(input_product_id, output_product_id)` связана внешним ключом с `materials`;
     - `step_number` — порядковый номер шага (уникален в рамках выпускаемого изделия);
     - `equipment_name`, `work_center_name` — используемое оборудование;
     - `operation_class_id` — вид операции (проверяется принадлежность ветке `operation`);
     - `profession_id` — профессия исполнителя (проверяется принадлежность ветке `profession`);
     - `labor_cost` — трудоемкость операции в человеко-часах;
     - `operations_parameters` — технологические параметры операции (например, температура, время выдержки).

## 4. Как работает бизнес-логика (Ключевые сценарии)

### 4.1 Создание модификации изделия
1. При создании продукта указывается `base_id` (ссылка на базовый рецепт/шаблон).
2. База данных и сервис автоматически копируют базовый состав компонентов из `materials` базового изделия с отметкой `base = true`.
3. Пользователь может переопределить индивидуальные параметры изделия через `products_parameters`.

### 4.2 Создание и валидация технологической операции (`OperationService.CreateOperation`)
1. **Проверка полей**: проверка на непустое имя, положительный `step_number`, неотрицательный `labor_cost`.
2. **Проверка иерархии классов**: сервис рекурсивно поднимается по дереву `classes` и проверяет, что `operation_class_id` уходит корнем в ветку `operation`, а `profession_id` — в ветку `profession`.
3. **Проверка спецификации BOM**: проверяется, что пара `(input_product_id, output_product_id)` реально зарегистрирована в таблице `materials`.
4. **Валидация технологических параметров**: сопоставление переданных параметров со спецификацией класса операции (`range_parameters` и `enum_parameters`).
5. **Транзакционное сохранение**: запись в `operations` и атомарная вставка параметров в `operations_parameters`.

### 4.3 Формирование техкарты и расчет себестоимости (`GetProductTechCard`)
Эндпоинт: `GET /api/products/{id}/operations?quantity={N}`

1. **Рекурсивный обход BOM-дерева**:
   - Сервис обходит дерево состава на всю глубину (от готовой бутылки через все полуфабрикаты до базового сырья).
2. **Сбор технологических операций**:
   - Для каждого промежуточного полуфабриката и конечного продукта загружаются все привязанные операции, отсортированные по `step_number`.
3. **Расчет потребности в материалах и полуфабрикатах**:
   - В обратном топологическом порядке вычисляются требуемые объемы каждого полуфабриката для выпуска заданного объема готовой продукции `quantity`.
   - Суммируются сводные нормы расхода покупных материалов (`is_purchased = true`).
4. **Калькуляция сырьевой себестоимости**:
   $$\text{MaterialCost} = \sum (\text{Норма расхода материала}_i \times \text{Цена}_i)$$
5. **Калькуляция стоимости труда**:
   - Для каждой операции определяется профессия исполнителя.
   - Из числового параметра `hour_salary` класса профессии извлекается часовая тарифная ставка.
   - Затраты на операцию:
     $$\text{LaborCost}_{\text{op}} = \text{hour\_salary} \times \text{labor\_cost} \times \text{Количество выпускаемого полуфабриката}$$
   - Суммируются затраты по всем операциям всех этапов производства.
6. **Итог**:
   $$\text{TotalCost} = \text{MaterialCost} + \text{LaborCost}$$
   Возвращается полная структура `ProductTechCard`: список всех операций, сводные нормы расхода материалов и итоговая себестоимость.

## 5. Запуск и развертывание

### Локальный запуск через Docker Compose:
```bash
# Запуск PostgreSQL, Nginx, Prometheus, Grafana
make buildup
# или
docker-compose -f deployments/docker-compose.yml up -d
```

### Накатывание миграций и запуск приложения:
Миграции применяются автоматически при старте `cmd/main.go`:
```bash
go run cmd/main.go
```
Для заполнения базы готовыми тестовыми сценариями (дерево категорий, сырье, пиво, техмаршруты, оборудование, сотрудники):
```bash
make filldb
```

### Проверка работоспособности:
- Swagger UI / OpenAPI: `http://localhost:8080/api` (или `http://localhost:80/api` через Nginx)
- Метрики Prometheus: `http://localhost:9090`
- Дашборды Grafana: `http://localhost:3000`
- Запуск юнит-тестов: `go test ./...`
